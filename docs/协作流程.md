# 协作流程（小白版）

> 一句话：**`main` 是正式版，谁都不能直推。你干一件事，开一个分支，做完提 PR，合完删分支。**

---

## 第 0 步：clone 之后做一次

```bash
git config core.hooksPath .githooks
```

做完这一步，你在 `main` 上直接 `git push` 会被本地拦住，并提示该怎么做。
这是防手滑的，不是限制你。

---

## 例 1：我只改了一个文档

```bash
git checkout main
git pull
git checkout -b docs/补充Mac说明

# 改文件……

git add docs/环境搭建.md
git commit -m "docs: 补充 Mac 安装步骤"
git push -u origin docs/补充Mac说明
```

推送后终端会打印一个链接，点开就是「Create pull request」。

写完标题和说明，点绿色按钮。合并之后回来清理：

```bash
git checkout main
git pull
git branch -d docs/补充Mac说明
```

## 例 2：我加了一个转码脚本

```bash
git checkout main
git pull
git checkout -b feat/转码矩阵-mp3三档

# 写 tools/transcode_matrix.py
# 本地跑一遍，确认能出结果

git add tools/transcode_matrix.py
git commit -m "feat: 加 MP3 三档转码脚本"
git push -u origin feat/转码矩阵-mp3三档
```

PR 说明里写清楚：**跑了什么命令、产出了什么文件、结果是多少**。

## commit message 怎么写

格式：`类型: 一句话`

| 类型 | 什么时候用 |
|---|---|
| `feat` | 加了新功能、新脚本 |
| `fix` | 修了 bug |
| `docs` | 只改文档 |
| `test` | 加测试 |
| `chore` | 配置、依赖、杂务 |

| 好的 | 坏的 |
|---|---|
| `feat: 加 MP3 128/64/32k 三档转码脚本` | `update` |
| `fix: 修复 8766 端口占用时的启动报错` | `改了一下` |
| `docs: 补充 Mac 安装步骤` | `111` |

写清楚"改了什么"，不用写"为什么"——那放 PR 说明里。

---

## PR 说明写什么

三句话就够：

```
改了什么：加了 tools/transcode_matrix.py，按码率跑三档 MP3
为什么：题面要求压缩加噪测试，MP3 目前是空白
怎么验证的：示例音频 4.39s，跑三档，128k 能取回，64k 取回，32k 失败
```

失败也要写。**写"32k 失败"比写"全部通过"有价值得多。**

## 冲突了怎么办

看到 `CONFLICT` 别慌，按顺序试：

```bash
git checkout main
git pull
git checkout 你的分支名
git merge main
```

- 如果自动合并成功 → `git push` 继续；
- 如果提示某个文件冲突 → **别自己硬改，喊组长**；
- **任何情况下都不要 `git push -f`。**

---

## 五件不要做的事

1. **不要 `git push -f`。** 会覆盖别人的提交，恢复起来非常麻烦。
2. **不要往 main 直推。** 本地钩子会拦，`--no-verify` 能绕，但绕了就是破例。
3. **不要提交大文件。** `*.wav`、`*.pt`、模型权重、语料，一个都不要。GitHub 拒收 100 MB 以上，而且进了历史很难清。
4. **不要一个 PR 改十件事。** 一个 PR 一件事，出问题好回滚。
5. **不要改完 `core.py` 不说。** 它是嵌入核心，改了会让结果和论文数字对不上。

---

## 分支活多久

**不超过两周。** 超过两周说明任务切太大了，拆成两个。

分支攒着不合，最后一定冲突；冲突一多，人就不想合了；不合，就等于白干。
