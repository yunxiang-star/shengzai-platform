# 语音隐写演示台

一个给第一次接触的人用的本地 Web 演示：

**上传 WAV → 输入 2 / 4 位十六进制短口令 → 真跑 EnCodec → 听藏字音频 → 下载 → 再提取。**

不是假动画，也不是“把字节塞进文件尾巴”。它真的在 EnCodec 的 L0 索引上写入，然后落成 PCM16 WAV，再重新编码、去交织、纠错、取回。

## 2. 第一次用怎么点

1. 点 **“用示例音频”**。默认会载入一段约 4 秒的真人语音。
2. 默认口令是 `C0`，即 2 位十六进制 / 8 bit。它是推荐档：载波更少，失真更低，现有同链路测试中的完整恢复率也高于 16 bit。需要更大载荷时可切到 16 bit（如 `C0DE`）。
3. 密钥保持 `demo-2026`。
4. 先选 **“直接换抽屉”**，点 **“开始把口令藏进去”**。
5. 等 2–8 秒，页面会显示：
   - 8 bit 写入/取回对比（默认，可切换 16 bit）；
   - “重编码后原始比特存活率”；
   - 错钥匙会读到什么；
   - 公开/藏字音频试听；
   - 前 24 个载波索引的“旧编号 → 新编号”；
   - 发送端/接收端直方图；
   - 下载按钮。
6. 再选 **“换座位，不换书单”** 跑一次，对比“发送端直方图 L1 应该接近 0”。
7. 到 **“提取验证”** 页，上传刚下载的藏字 WAV，模式/密钥保持一致，填期望口令，点提取。

## 3. 页面上每条线是什么意思

| 页面元素 | 真实含义 |
|---|---|
| EnCodec 24 kHz | 声音被压成每秒 75 帧的 RVQ 索引；6 kbps = 8 层、12 kbps = 16 层、24 kbps = 32 层（演示默认 24） |
| L0 索引 | 第 1 层量化器的编号，取值 0–1023 |
| 口令长度 8 / 16 bit | 默认 8 bit（2 位十六进制）；载波 42，相比 16 bit 的 66 个载波少改约 40% |
| 卷积码 | 纠错，不是 STC；rate-1/3 或 1/4，配 Viterbi 解码 |
| 交织 | 按密钥打乱纠错比特顺序，避免连续擦除一锅端 |
| 原始比特存活率 | 重新编码后、**纠错前**，索引比特还对多少 |
| 纠错后结果 | 去交织 + Viterbi 后的消息是否完全一致（默认 8 bit，可选 16 bit） |
| 发送端直方图 L1 | 嵌入前后 L0 索引多重集的差异；HPP 严格为 0 |
| 接收端直方图 L1 | 保存 PCM16、重新编码后再次统计的差异 |
| STOI | 语音可懂度近似指标；**只反映可懂度，不能证明听不出来** |
| 分段 SNR / LSD | 局部失真与谱形偏差；要和「codec 自身的失真」对比才有意义 |
| AUC | 隐写分析器区分公开/藏字的可分性；0.5 ≈ 瞎猜，1.0 = 一抓一个准 |

三个页签：

- **嵌入实验**：跑一次嵌入，给出消息对照、存活率、STOI、直方图、波形差和 token 改动预览。
- **提取验证**：只上传藏字 WAV，按模式与密钥取回消息；可填期望口令做自动比对。
- **协议与威胁模型**：四张实测图（端到端链路、HPP 多重集、P/码率恢复率、三个观测面的 AUC），参数和失败模式都按实测写。

## 4. 两种模式到底差在哪

### 直接换抽屉（direct）

- 默认 8 bit + K=7 rate-1/3 卷积码 → 42 个载波；16 bit 时为 66 个；
- 密钥决定每个码字对里哪边是 0、哪边是 1；码字对本身用**最近邻完美匹配**（同一码本，1024 个码字两两配对，总距离最小）；
- 论文留出集：消息恢复 100%，索引直方图 AUC 0.921（论文用的是随机配对）。

优点：恢复最稳。  
缺点：索引使用次数会变，直方图分析器容易抓。

### 换座位，不换书单（HPP）

- 默认 8 bit + K=7 rate-1/3 卷积码 → 42 个载波；16 bit 时为 66 个（论文版是 conv14 / 88 个，这里为短音频稳定性改了配置）；
- P = min(128, 音频帧数)，其余位置做自由填充；
- 在载波集合内做最小代价双射置换；
- **嵌入前后码字多重集严格相同**；
- **发送前自检**：发送端自己先把候选藏法走一遍「解码 → 存 PCM16 → 再编码 → 取回」，确认能读回才交付；最多试 12 种合法置换（不同扰动 + 不同时间项权重）。接收端**不需要**知道试了几次。
- 演示台实测（4.39 秒示例音频，30 个随机口令）：完整恢复 **30/30**，全部第 1 次自检即通过；原始比特存活率 **0.881**，分段 SNR 约 24 dB。
- 论文留出集（P160/conv14、无自检）：消息恢复 97.5%，直方图 AUC 0.598。

优点：发送端全局直方图严格保持。  
缺点：**恢复率明显低于直接替换**，短音频上单次尝试只有约四到五成，靠自检重试才拉到九成；重新编码后仍有残余分布，LFCC 0.574、Nes2Net 偏移 0.645。

> **降级规则**：如果 HPP 试满 12 次仍读不回来，演示台会尝试「直接换抽屉」；只有备用模式也通过完整自检时才交付，并在结果卡上**明确标注已降级**、说明原因。

**完整提取自检是交付门槛**：首选模式和备用模式都无法完整读回时，页面返回错误，不生成交付 WAV。16 bit 失败会建议切到 8 bit；8 bit 失败会建议更换较长、静音更少的语音。

## 5. 听感：先分清是谁的锅

三段音频：① 原始 WAV → ② EnCodec 重建（不藏东西）→ ③ 藏字交付。  
**①→② 是 codec 的固有失真，②→③ 才是藏法引入的。** 混在一起谈就会把 codec 的锅算到隐写头上。

两个客观量（脚本 `tools/perceptual.py`、`tools/codec_diagnose.py`）：

| 指标 | 含义 | 方向 |
|---|---|---|
| LSD 对数谱距离 | 只在「参考信号本身有能量」的频点上算谱形偏差 | 越小越好 |
| 分段 SNR（20 ms） | 局部劣化 | 越大越好 |
| 掩码超阈比例 | 噪声超过「公开版能量下移 24 dB」的时频块占比，粗估 | 越小越好 |

示例音频实测（4.39 s，6 条口令平均，direct 用最近邻配对）：

| 对照 | LSD | 分段 SNR |
|---|---:|---:|
| ① 原始 → ② EnCodec 重建（**6 kbps**，论文档） | 9.07 dB | 10.82 dB |
| ① → ②（**12 kbps**） | 8.37 dB | 13.50 dB |
| ① → ②（**24 kbps**，演示默认） | 7.98 dB | 15.38 dB |
| ② 重建 → ③ 藏字（direct） | **1.55 dB** | **26.41 dB** |
| ② 重建 → ③ 藏字（HPP） | 3.11 dB | 21.62 dB |

**怎么读**：嵌入噪声比 codec 地板低 15 dB 左右。也就是说，这段音频里你听得到的「机器味」基本来自 codec，不是藏法。

**LSD 这个数改过一次。** 旧实现把 8–12 kHz 这种近乎空白的频带也算进去——两边都是 1e-10 量级，比值纯属数值噪声，把地板从 9 dB 抬到 21 dB。现在只统计参考信号高于本帧峰值 −60 dB 的频点，`core.perceptual_metrics` 已同步。

**整体音量适配**：嵌入和提取都会把送进 EnCodec 的波形统一到固定 RMS，并限制峰值；交付 WAV 会恢复输入音量。这样整体增益变化不会改变发送端与接收端使用的码本输入。本机自检覆盖了 PCM16 音量降低 10 dB 的情况。这个结果不代表能抵抗裁剪或有损转码。

**STOI 不能当透明性证据**：它只测可懂度，对咔哒、金属感、发闷几乎不敏感。历史论文里的 STOI 0.906 / 0.915 同样不能用来声称「听不出来」。

**仍未做**：PESQ / UTMOS（本机装不上，无 cp313 wheel）、正式盲听。现在的结论只是「嵌入噪声已低于 codec 地板」，不是「感知透明」。

**示例音频换过**：原来的 `demo.wav` 是 codec 自身失真最重的一段（分段 SNR 2.8 dB），已换成 `real_spk1988_05`（10.8 dB），旧文件保留为 `assets/demo_noisy_backup.wav`。

### 5.1 交付音质：换的是码率，不是采样率

「人机味」来自 RVQ 量化，不是采样率。

- **采样率没得加**：`encodec_24khz` 的输出带宽是 12 kHz，而素材本身是 16 kHz 录音（内容只到 8 kHz）。再往上换 48 kHz 模型，没有东西可编码，白付一倍算力。
- **真正的旋钮是 `bandwidth`，也就是 RVQ 层数**：

| 档位 | RVQ 层数 | 波形相关系数 | 分段 SNR（地板） |
|---|---:|---:|---:|
| 6 kbps | 8 | 0.910 | 10.82 dB |
| 12 kbps | 16 | 0.949 | 13.50 dB |
| 24 kbps | 32 | 0.963 | 15.38 dB |

**关键性质：第 0 层码字与总层数无关。** 同一段输入在 6 / 12 / 24 kbps 下编码，L0 **逐位相同**（12 与 24 kbps 的前 16 层也完全相同）——因为 RVQ 是先粗后细，总层数只决定后面加多少修正层。我们在 L0 上做隐写，所以：

> 对**同一个交付文件**，接收端用 6 / 12 / 24 kbps 任一层数重新编码，L0 完全相同，取回结果一致（实测两种模式 × 三档共 12 组全部成功）。换档改变的是交付波形本身，所以“同一段音频分别按 6 kbps 和 24 kbps 嵌入”仍是两个不同文件。

演示台因此默认 24 kbps，论文档 6 kbps 仍可一键切回。试听文件：`assets/preview_source.wav`、`preview_deliver_6k.wav`、`preview_deliver_12k.wav`、`preview_deliver_24k.wav`（同一段音频、同一条口令，只换档位）。

**边界**：24 kbps 只是「机器味更少」，不是透明；它仍然是 6→24 kbps 的神经 codec，不是原始波形。

### 5.2 载荷长度：唯一真正管用的质量旋钮

用户问「能不能像图像那边的 UNIWARD 一样再优化」。四种改法都试了，只有一条有效。

**有效的：把口令从 16 bit 降到 8 bit。** 载荷减半 → 载波从 66 降到 42 → 改动从 34 降到 20：

| 配置 | 载波 | 平均改动 | 完全恢复 | 分段 SNR | 有声频点 LSD |
|---|---:|---:|---:|---:|---:|
| 16 bit / conv13 | 66 | 34.2 | 64.6% | 22.66 dB | 2.82 dB |
| **8 bit / conv13** | **42** | **20.5** | **95.8%** | **26.66 dB** | **2.09 dB** |

（6 段音频 × 8 条口令 = 48 组，direct 模式、24 kbps。原始输出见 `runtime/payload_probe.log`。）

恢复率之所以**反而更高**：载波少了 36%，被 codec 擦掉的机会也少了 36%，而纠错强度没变。

**试过但不成立的四条路**（都在 `tools/` 里留了脚本与数据）：

| 尝试 | 结果 | 原因 |
|---|---|---|
| STC + 感知代价（全 330 位） | 改动 32.5 → **17.5**，分段 SNR 26.7 → **30.5 dB**，但 syndrome 准确率 **0.00–0.18**，一条都解不出 | syndrome 是全局的：信道擦掉 15% 的 token，每次擦除污染 h/2 个 syndrome 位，6 位一块全灭 |
| 码率降到 1/2（44 载波） | 示例音频上更好，但 6 段音频平均 **33.3% vs 64.6%** | 载波少了，纠错也弱了；单段结果不可外推 |
| 咬尾卷积码（省掉 18 个尾比特，48 载波） | **0%** | 16 bit 的短块咬尾码最小距离太低，64 个起始状态里更容易选到错的 |
| 接收端盲判码率（按重编码距离挑） | **75%** | 两种码率的载波位置不同，弱的那个假设也能凑出低分 |

**结论**：STC/UNIWARD 那套「最小失真」在这条链路上不成立，因为它的前提是**信道干净、错误稀疏**；我们的信道是 15% 的擦除信道。想继续降失真，只能降容量，或者在信道侧动手（提高 token 存活率）。

试听：`assets/preview_deliver_16bit.wav` 与 `preview_deliver_8bit.wav`（同一条音频，只换载荷长度）。

## 6. 它**不是**什么

- **不是加密工具。** 密钥只是映射钥匙，不是密码学加密。
- **不是 STC。** 当前用的是码本配对 + HPP 最小代价置换 + 卷积纠错；STC 尚未接入。
- **不是任意音频都鲁棒。** 只验证 EnCodec 24 kHz / PCM16 同链路（6/12/24 kbps 三档互通）；MP3、微信、重采样、裁剪、降噪未验证。
- **不是不可检测。** HPP 只是显著削弱了一个显式侧信道，不能写“统计不可区分”。
- **不是生产服务。** 上传只到本机 Python 进程；密钥在页面里是明文；仅用于课程/科研演示。

## 9. 常见问题

**上传后按钮还是灰的？**  
只接受 `.wav`；文件必须能被 `soundfile` 读出。

**页面报“装不下这个口令”？**  
HPP 要保持多重集不变。如果这段音频的索引分布太偏、填充位不够，就无解。换口令或换音频即可，不是浏览器坏了。

**提取出来是乱码十六进制？**  
十有八九模式、密钥或口令长度不一致。默认 8 bit 时 direct 和 HPP 使用 42 个载波；16 bit 时使用 66 个。两种模式的置换方式不同，用错模式也会读不出来。

**我选的是「换座位」，结果却显示「直接换抽屉」？**  
说明 HPP 试满 12 种合法置换都没读回来，演示台自动降级了。结果卡上会明确写“已改用直接替换”，并说明原因。这是有意的：宁交付一条能读回的音频，也不交付一条读不回的，更不假装 HPP 成功。想再赌一次可以点“换一组随机再试”。

**HPP 是不是很不稳？**  
以前在旧示例音频上确实是：单次尝试只有四五成，靠自检重试才到 93.3%。换了示例音频（`real_spk1988_05`，codec 自身失真低 8 dB）并改成 P=128 后，30 个随机口令 **30/30**、全部一次通过。所以“难不难”高度依赖素材本身——论文那批留出集是 97.5%，独立复现 102/105。**这件事已经核对过**：`02_隐写实验/paper_hpp_reproduction/`。

**下载后再上传读不出来？**  
鲁棒性探测目前是小样本：4 段音频 × 原音量 / 发送端降低 10 dB，再对交付 PCM16 降低 10 dB，8/8 完整读回；另 2 段音频 × direct/HPP，16 kHz 往返重采样 4/4 读回。3.4 kHz 低通和 30 dB 噪声各为 3/4；开头补静音或裁掉 40 ms 后为 0/4。MP3、平台二次编码尚未验证。交付档位 6/12/24 kbps 可互提，正式验证链路仍是 PCM16 WAV。

**为什么服务启动很慢？**  
第一次加载 `facebook/encodec_24khz` 要几秒；之后本进程内常驻。
